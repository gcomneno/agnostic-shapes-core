# Agnostic SHAPES Core Status

## Current architecture

**Agnostic SHAPES Core (ASHES)** is the maintained project container.

**SHAPES** is the interpretation-agnostic structural core.

**PETRA — Prime Exponent Tower Recursive Algebra** is one maintained,
pluggable prime/exponent interpretation layer over SHAPES.

**PIP — the Prime Interpretation Problem** is foundational theory inside PETRA.

The dependency direction is:

```text
PETRA -> SHAPES
future interpretation -> SHAPES

SHAPES -X-> PETRA
PETRA -X-> future interpretation
```

The pre-separation structural `petra` runtime has been retired.

Historical PET and PETRA terminology remains preserved where it identifies
historical contracts, releases, research, or evidence.

## SHAPES canonical theory

The normative SHAPES carrier is:

```text
S ::= Node(M_f(S))
```

where every node has a finite multiset of child forms.

The canonical theory establishes:

- primitive direct parent-child incidence;
- intrinsic child multiplicity;
- no intrinsic sibling order;
- recursive multiset structural equality;
- `Node(empty multiset)` as the unique zero-child form;
- intrinsic structural size;
- the intrinsic elementary edit algebra generated by `ADD` and `REMOVE`;
- exact inverse relation between `ADD` and `REMOVE`;
- separation of structure, representation, and interpretation.

The sole normative source for SHAPES semantics is:

```text
docs/reference/SPEC.md
```

## Maintained SHAPES runtime

The maintained structural runtime lives under:

```text
src/shapes/
```

Its current public API exports:

- `Shape`;
- `OccurrencePath`;
- `size`;
- `add`;
- `remove`;
- `iter_occurrences`;
- `validate`.

`OccurrencePath` is a state-scoped representation for targeting concrete
occurrences in one current runtime state.

It is not persistent node identity and does not participate in SHAPES
structural equality.

No prime assignment, exponent interpretation, represented integer value,
primality test, factorization rule, or PETRA-specific interpretation policy is
part of the SHAPES core.

## PETRA interpretation layer

The normative PETRA interpretation contract is defined by:

```text
docs/reference/PETRA.md
```

PETRA consumes already-existing SHAPES forms.

It must not redefine:

- SHAPES structural equality;
- multiplicity;
- sibling non-order;
- occurrence semantics;
- intrinsic `ADD`;
- intrinsic `REMOVE`;
- intrinsic size.

The maintained PETRA runtime lives under:

```text
src/petra/
```

Its current public API exports:

- `LRPE`;
- `LRPEPolicy`;
- `MaterializationLimits`;
- `MaterializationLimitError`;
- `ReverseDomainError`.

LRPE — Local-Rank Paired-Exponent — is the first maintained executable PETRA
interpretation policy.

Its promotion does not identify PETRA with LRPE and does not establish an
implicit universal default interpretation.

PETRA remains an interpretation-policy space over SHAPES.

## PIP status

PIP remains the mechanism for studying and classifying candidate PETRA
interpretation policies.

The completed Phase 3 research established:

```text
Matula–Göbel
    reference interpretation
    faithful
    bijective with N+

LRRE
    research candidate
    non-faithful

LRPE
    maintained policy
    faithful
    proper decidable image
    effective inverse on its image
```

Policy-specific properties such as faithfulness, image characterization,
reverse interpretation, and computability do not become SHAPES semantics.

## Resolver satellite

`resolver/` remains a separately packaged satellite.

Its package metadata describes it as:

```text
Resolver satellite over the SHAPES structural core
```

Resolver is outside the ASHES core release and test contract.

Its own package version remains independent of the root
`agnostic-shapes-core` distribution.

Resolver does not define SHAPES or PETRA semantics.

## Distribution and package identity

The maintained distribution name is:

```text
agnostic-shapes-core
```

The maintained Python packages are:

```text
shapes
petra
```

This distinction is intentional.

The `petra` Python package is the maintained interpretation layer, not a
compatibility alias for the SHAPES structural core.

## Release history

Published PETRA releases remain historical releases under their original
identity.

In particular, the published `v2.1.0` Zenodo record remains PETRA historical
evidence and must not be retroactively renamed.

Future releases under the current repository identity use:

```text
Agnostic SHAPES Core
```

with the informal project nickname:

```text
ASHES
```

The existing Zenodo concept DOI family is retained across that historical
continuity.

## Research boundary


canonical specification and implementation process.

current SHAPES or PETRA semantics.
